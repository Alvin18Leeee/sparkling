# Sparkling 下载器 —— 总体架构与子项目①（HTTP 下载核心）设计

日期：2026-08-28
状态：待用户审阅

## 背景与目标

Sparkling 是一款 PC 端全功能下载器，目标形态类似 Motrix / FDM：

- **能力范围**：HTTP/HTTPS 多线程下载、BT/磁力、流媒体视频解析下载
- **目标平台**：Windows 优先，架构预留跨平台（不硬编码平台 API，技术栈全跨平台）
- **技术栈**：Tauri 2 + Rust（核心层独立 crate）+ React + TypeScript（前端）
- **产品定位**：公开发布的产品（安装包、自动更新、多语言等发布级要求在后续子项目补齐）

## 范围与路线图

本设计文档包含两部分：**总体架构**（约束所有子项目）与**子项目①的详细设计**（本次实现范围）。每个子项目走独立的 spec → 计划 → 实现周期。

| 期 | 交付物 | 状态 |
|---|--------|------|
| ① | HTTP/HTTPS 多线程下载 + 任务队列 + 断点续传 + 限速 | **本文档范围** |
| ② | BT/磁力引擎（接入 crane 或 aria2 sidecar，届时评估） | 后续独立 spec |
| ③ | yt-dlp 视频解析 + m3u8 下载合并 | 后续独立 spec |
| ④ | 浏览器接管、剪贴板监听、批量导入、自动更新、多语言 | 后续独立 spec |

**引擎决策（方案 C，混合引擎）**：HTTP 自研原生 Rust 引擎；BT 后插；视频包装 yt-dlp。`Engine` trait 是唯一的引擎边界，上层只认识"提交 URL → 进度流 → 结果"，后续引擎是"接入"而不是"重构"。

## 总体架构

```
┌─────────────────────────────────────────────┐
│  WebView 前端（React + TypeScript）           │
│  任务列表 / 任务详情 / 设置 / 全局速度面板      │
└──────────────┬──────────────────────────────┘
               │ Tauri commands (调用) + events (推送，节流 250ms)
┌──────────────┴──────────────────────────────┐
│  Rust 核心层（sparkling-core，独立 crate）    │
│  ├─ TaskManager：队列 / 并发 / 优先级         │
│  ├─ TaskStore：SQLite 持久化（rusqlite）      │
│  └─ Engine trait：下载引擎抽象（扩展点）      │
│       ├─ HttpEngine（①，自研多线程分片）      │
│       ├─ BtEngine（②，后插）                 │
│       └─ VideoEngine（③，包装 yt-dlp）       │
└─────────────────────────────────────────────┘
```

关键约束：

1. **sparkling-core 不依赖 Tauri**：纯 Rust 库，引擎与调度逻辑可脱离 UI 完整测试。
2. **UI ↔ 核心通信**：命令走 Tauri commands（invoke）；进度走 Tauri events，节流约 4 次/秒。
3. **未来的 sidecar（yt-dlp 等）由 Tauri sidecar 机制管理**，不进入本期的 sparkling-core。

## 子项目①：HTTP 多线程下载引擎

### Engine trait（示意）

```rust
trait Engine {
    async fn submit(&self, task: TaskSpec) -> Result<TaskHandle>;
}
// TaskHandle：进度事件流、pause/resume/cancel、
// 每分片状态（供 UI 绘制分片进度）、错误
```

### 分片调度器

- **探测**：先发 HEAD（或 `Range: bytes=0-0`）确认：是否支持 Range、文件大小、文件名（Content-Disposition）。
- **固定分片**：按文件大小切 N 段（默认 8，可配 1–64），每段独立连接、独立写入偏移。
- **动态偷段**：某段提前完成时，将最慢段的剩余部分分裂过来，消除长尾。
- **降级**：服务器不支持 Range → 单线程顺序下载，UI 如实标注。

### 断点续传

- 每任务伴随控制文件 `<文件名>.sparkling`（JSON）：分片表 + 每段已写偏移；每 2 秒或有分片完成时落盘。
- 数据写入 `<文件名>.sparkling.part`（预分配大小，分片各写各的偏移）。
- 恢复：读取控制文件 → 校验文件大小与已下载偏移一致 → 继续；不一致 → 任务 Failed。
- 任务完成后删除控制文件，`.part` rename 为正式文件名。

### 限速

- 全局 + 单任务两级，令牌桶算法，实现在调度器层（所有分片共享），配置实时生效。

### TaskStore

- SQLite（rusqlite），核心表 `tasks`（URL、状态、保存路径、配置）。
- 运行时状态在内存，变更时写库；启动时加载未完成任务入队。

## 任务状态机与数据流

```
Queued ──调度──▶ Running ──完成──▶ Completed
  ▲                 │ │
  │            暂停 │ │ 失败(可重试)
  │                 ▼ ▼
  └──────────── Paused / Failed
                     │ 手动重试 / 自动重试
                     └──▶ Queued
任意未完成状态 ──取消──▶ Cancelled（清理控制文件与分片数据）
```

- **并发控制**：同时运行任务数默认 3（可配），其余排队；队列支持手动置顶。
- **Paused**：暂停所有分片，保留上下文可快速恢复。
- **一次下载数据流**：粘贴 URL → invoke add_task → SQLite 建 Queued 记录 → 调度有空位 → HttpEngine.submit → 探测 → 生成分片表 → N 分片并发写 `.part` → 进度事件（节流）→ 全部完成 → 若响应头含 Content-MD5 则校验 → rename → Completed → 控制文件删除 → 调度下一任务。（ETag/Last-Modified 仅用于续传时的变化检测，不作为完整性校验。）
- **重启恢复（产品决策）**：启动时加载未完成任务，Running/Paused 的任务**自动恢复下载**（设置留开关，默认开启）；控制文件校验失败的任务标为 Failed，不影响其他任务。

## 错误处理

**网络层**
- 单分片失败：分片级重试，指数退避 1s/2s/4s…（上限 30s），5 次后该分片失败。
- 全部分片重试耗尽 → 任务 Failed，详情记录错误；手动重试从分片断点继续。
- 416（Range 非法）：重置该分片从头下载；5xx/DNS/连接失败走重试策略。

**服务器能力**
- 不支持 Range：降级单线程，UI 提示。
- **数据正确性红线**：续传时 ETag/Last-Modified 与记录不一致 → 视为文件已变化，整个任务从零重下并清理旧分片。宁可重下，不产出损坏文件。

**磁盘层**
- 下载前检查剩余空间（文件大小 × 1.02），不足直接 Failed 并明确提示。
- 写入失败（磁盘拔出/权限）：任务 Failed，保留控制文件，支持"另存为后继续"。

**进程层**
- 崩溃/强杀：下次启动靠控制文件恢复；控制文件损坏（JSON 解析失败）→ Failed 并提示重新下载，同样不产出坏文件。

**错误呈现**：统一 `SparklingError` 枚举，两层信息——用户可读中文消息 + 技术细节（状态码、URL 片段）；UI 默认显示前者，详情面板显示后者。

## 测试策略

原则：sparkling-core 不依赖 Tauri，绝大部分测试为纯 Rust 测试。

**单元测试**（`cargo test`）
- 分片数学：0 字节 / 小于分片数 / 整除 / 巨大文件的切分与再分裂。
- 控制文件：写入、截断模拟（崩溃）、解析失败路径。
- 状态机：全部合法/非法转换。
- 令牌桶速率近似正确性。

**集成测试**（可编程本地 HTTP 测试服务器，axum，127.0.0.1 随机端口）

| 服务器行为 | 验证 |
|-----------|------|
| 正常支持 Range | 完整下载，SHA-256 与源一致 |
| 不支持 Range | 降级单线程且内容正确 |
| 传输中途掐断连接 | 分片重试、退避，最终完整 |
| 限速 + 动态偷段 | 无长尾、总时长合理 |
| 二次请求 ETag 变化 | 检测到并从零重下 |
| 416 / 5xx | 按策略处理 |

**崩溃恢复测试**：下载至 40% 时 kill 进程 → 重启恢复 → 完成后整体哈希校验一致。

**UI 层**：①期仅冒烟测试（应用启动、command 添加任务、进度事件到达前端）；自动化 E2E 留待④期。
